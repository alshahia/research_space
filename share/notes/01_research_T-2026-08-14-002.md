## What we know for sure (merged)

- **Single-player RTS in Unity is feasible with HIGH confidence.** Every required system has a verified Unity path (input, pathfinding, FoW, economy, save, UI, camera) and multiple complete RTS tutorials/repos prove the loop is buildable. Verdicts: core yes/HIGH, AI yes/HIGH, OSS feasible/HIGH, techniques yes/MEDIUM. The only verdict-flipping unknowns are user decisions (unit scale, 2D/3D), not technical blockers.
- **No OSS cornerstone exists.** Every Unity OSS RTS is GPL, unlicensed, MIT-but-stale, or multiplayer-focused. Verdict: build from scratch, informed by a learn-from constellation (MinaPecheux MIT + OpenRA/0 A.D. architecture + Warzone2100 single-player AI). Strict no-code-reuse rule for GPL/unlicensed repos (license contamination = HIGH risk).
- **Default architecture: GameObject/MonoBehaviour + ScriptableObject data + event bus.** Matches every current Unity RTS course/repo; cheapest to build and debug. DOTS/ECS only at horde scale (thousands of units) or when profiling proves it. Hybrid (OOP + Jobs/Burst hot loops) is the recommended middle path. Lockstep/netcode frameworks exist but are the wrong tool for local single-player - avoid.
- **Opponent AI = hand-authored hierarchical AI** (strategy/tactical/reactive layers + scripted build orders + handicap difficulty dials). Proven by TStarBot2 (beat all 10 SC2 built-in AI levels) and UAlbertaBot (SC2 GM rank 19 NA). RL and LLM opponents are NOT viable for v1 (compute, Mono-only training, latency/network violates constraints).
- **Unity 6.3 LTS is the current release line** (supported to Dec 2027); Unity 6.0 LTS ends Oct 2026. Baseline stack: Unity 6.3 LTS + URP + new Input System + AI Navigation 2.0. Pin everything; docs drift fast (multiple minors live simultaneously).
- **Save: BinaryFormatter is dead** (removed in .NET 9). Use JsonUtility (built-in) or Json.NET for Unity over `[Serializable]` DTOs with a version field; never serialize UnityEngine.Object references.
- **Rendering contract:** URP + SRP Batcher + GPU instancing (one atlased material per faction) + GPU Resident Drawer (evaluate late, profile before/after). Skinned Mesh Renderers are NOT instanceable.
- **Fog of war:** render-texture visibility mask (display) + CPU-side visibility grid (explored/visible) that the AI perception layer reads - fairness architecture built in.
- **Pathfinding families by scale:** NavMesh (tens of agents, MVP) -> grid A* (A* Pathfinding Project) -> flow fields (hordes). Design the movement abstraction (interface + NavMesh impl) from day one so the upgrade is a swap, not a rewrite.

## Merged findings by theme

### Core systems (angle-core, 36 findings)
- Selection: click + marquee + Shift add/remove; implement against a selectable registry/spatial hash, not per-frame physics raycasts on hundreds of units.
- Orders: command pipeline with serializable order structs (type, targetId, position, queue slot); Shift queues orders; same pipeline reused by the AI.
- Formations: slot assignment at order-execution time (square/arrow/circle); cheap and standard.
- Movement: AI Navigation 2.0 (built-in) for MVP; A* Pathfinding Project (de-facto standard, free tier, Burst/ECS since v5.0) for grid A*; flow fields for armies. NavMesh is NOT natively DOTS-compatible.
- Economy: harvesters -> drop-off -> stockpile -> costs; queue-based production. Buildings: grid snap + validity + ghost preview + construction progress + NavMesh carving hook on completion.
- Camera: WASD/edge pan + wheel zoom + rotate + minimap jump; trivially isolated CameraRig (build first, zero dependencies).
- Input: new Input System with named actions (SelectUnit, BoxSelectDrag, MoveOrder, AttackOrder, QueueModifier, camera actions) - action names become the contract.
- Save: DTO classes + JsonUtility/Json.NET + version field; serialize orders/queues/FoW grid.
- Avoid: lockstep/netcode frameworks, BinaryFormatter, hard-wiring NavMeshAgent into unit brains.

### Opponent AI (angle-ai, 26 findings)
- Three-layer shape: strategy (0.5-2s tick), tactical (0.1-0.3s tick), reactive (per-frame/event). Perception layer FIRST (fairness, scouting, difficulty all route through it).
- Build orders = data-driven scripts (ScriptableObjects/JSON), not code. Economy = priority system. Attacks = timers + strength thresholds. Scouting = scripted sub-AI. Defense = reactive priority list.
- Difficulty = handicap dials (resource multiplier, reaction latency, vision flag). SC2 cheats at top levels (documented); AoE2 DE extreme AI claims honest (players dispute). User decides the philosophy. DDA (dynamic difficulty adjustment) is verified, cheap, player-facing.
- Techniques: FSM for unit micro; behavior trees for commander/unit behavior (Behavior Designer paid / NodeCanvas paid / hand-rolled free); GOAP for worker/build logic (ReGoap free, license-verify); HTN natural fit for build orders; utility AI for army composition/target selection. Scripted version IS the baseline product - no planner before it works.
- Avoid for v1: RL opponent (AlphaStar-scale compute), LLM-at-runtime AI (latency + network), dead/unverified components (TheKiwiCoder BT 404, Panda BT unreachable), cheating-by-vision on normal difficulties.
- Debug visualization is part of the AI build (decision logging + Gizmos), budget it as a task.

### New techniques (angle-techniques, 16 findings, 52 sources)
- Unity 6.3 LTS baseline (Dec 2025, supported to Dec 2027); 6.2 GA unverified (404); 6.0 LTS ends Oct 2026.
- DOTS/ECS: verified-viable (A* Project v5.0 ships Burst/ECS; Unity's own RTS evidence: Door 407, Megacity Metro) but payoff at scale only; OOP + pooling + Jobs/Burst is the default.
- Pathfinding: NavMesh (MVP) -> grid A* (A* Project) -> flow fields (mass) -> HPA* (large maps, published research Harabor & Botea 2008). RVO2 OSS exists (960 stars) for crowd avoidance; typically consumed via A* Pro or custom separation.
- Rendering: URP + SRP Batcher + instancing + GPU Resident Drawer (43.5k->128 draw calls measured, but ~100MB memory, longer builds, Forward+ required); GPU occlusion culling (not baked CPU culling for open maps); Terrain for MVP, mesh ground when profiling says so.
- FoW: render-texture visibility mask (community standard, OSS cribs: AsehesL/FogOfWar, xddemir/Unity-Fog-of-War) + tile-based shadowcasting alternative; compute-shader path for huge maps.
- UI: UI Toolkit for HUD/menus (Unity's own recommendation for intensive UI), uGUI for world-space bars. IMGUI = editor legacy.
- Camera: Cinemachine 3.1 explicitly supports RTS; FreeLook rigs (ATerribleKingdom pattern).
- Save: JsonUtility `[Serializable]` DTOs, no Dictionary (unsupported), JSON to persistentDataPath; never BinaryFormatter (always throws).
- Procedural: FastNoiseLite (standard noise lib) for maps; WFC optional polish (license NOASSERTION - verify).
- Hype filter: proven = NavMesh, A* Project, instancing+SRP Batcher, render-texture FoW, JsonUtility, new Input System, Cinemachine, UI Toolkit. Conditional = full DOTS, GPU Resident Drawer, WFC, flow fields, RVO, ML-Agents RL.

## Build vs. reuse decisions (consolidated, need user input)

1. Pathfinding: reuse AI Navigation 2.0 for MVP, A* Pathfinding Project free tier when grid A* needed, flow fields only if mass movement demands. Build from scratch only if profiling demands (2-3 weeks).
2. Full RTS framework: learn-from OSS (recommended) vs paid template (none verified available - RTS Engine delisted) vs build from scratch.
3. Architecture: GameObject/MonoBehaviour + SO + event bus (default) vs DOTS from day one (horde scale only) vs hybrid.
4. Save system: JsonUtility (zero deps) vs Json.NET for Unity (community standard, dictionaries/polymorphism).
5. UI: uGUI everywhere (simplest) vs UI Toolkit for HUD + uGUI world-space (modern split).
6. AI framework: Behavior Designer ($90, paid) vs NodeCanvas (paid) vs minimal custom FSM + priority rules (free, ~1-2 weeks).
7. GOAP layer (if wanted): ReGoap (free, verify license) vs build from scratch (~1 week).
8. Learning-based opponent (optional post-v1): Unity ML-Agents single micro-behavior experiment vs skip.
