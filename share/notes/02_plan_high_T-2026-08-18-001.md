## Goal

Deliver an implementation-ready, source-cited documentation dossier that lets any agent or LLM use the OpenCode SDK safely, plus a bounded live-validation evidence file that proves the SDK actually reaches the OpenCode Zen free target and, after a separate user gate, optionally the OpenCode Go backup under approved cost and safety bounds. The dossier covers v1 as the public baseline, an explicit v2 delta with import paths and a version probe, both server-owning and existing-server runtime patterns, CLI prerequisites and PATH/version checks, a unified API map, lifecycle / security / error / event guidance, known issues with mitigations, verified TypeScript examples, and a reader-facing progress file. The evidence file documents the live-validation matrix results with sanitized reproduction data, official-issue matches, verdict taxonomy, and cleanup confirmation.

## Approach

1. **v1 baseline, v2 as a delta.** Every page that mentions a method, event, type, or default writes the v1 story first and then attaches a small v2-delta block (v2-only events, workspace header, HTML guard, `data.message.user` helper). The unified API map in `04_api_map.md` uses one row per method with a `(v1)` / `(v2-only)` / `(both)` marker so the reader never has to consult two parallel tables.

2. **Both runtime patterns in one dossier.** A long-lived agent that owns the server and a short-lived script that connects to an existing `opencode serve` are first-class readers. The reading map (`00_README.md`) exposes two paths; quickstart (`02_quickstart.md`) ships both recipes; the decision guide (`03_decision_guide.md`) names which to pick and why.

3. **Prerequisites before recipes.** The reader cannot copy a recipe if the CLI binary is missing. `01_prerequisites.md` documents the install methods (npm `opencode-ai`, brew, choco, scoop, mise; [S3]), the PATH check, a `GET /global/health` preflight that returns `{ healthy, version }` [S2], and a comparison snippet that records CLI version vs SDK version so skew is visible at boot rather than on first prompt. The version-skew wording uses **`same-minor-patch-delta-15`** (CLI 1.18.3 and SDK 1.18.18 share major=1 and minor=18 with patch delta = 15); **observed compatibility** is determined by health + the actual auth-free calls in 3E1, not by semver alone.

4. **Source-grounded everywhere.** Every factual SDK claim that the dossier repeats from research carries an inline `[Sn]` citation. `99_sources.md` is the canonical mirror of the research ledger (S1..S22) with access date and category grouping. am-coder cannot invent body shapes for endpoints whose shape research did not verify; the plan flags these as "writer must re-validate against `types.gen.ts` at write time" tasks and as a verification gate (see `## Writer verification tasks`).

5. **Examples are testable, not decorative.** Each example in `09_examples.md` carries: purpose, expected behavior or output, safety note (green safe / yellow warning / red unsafe), and the smallest runnable validation method (e.g., `bun run examples/quickstart-embedded.ts` exits 0 and a session id is logged). Required examples per the user task: embedded server + client, existing-server connection, session CRUD, prompting with explicit model, events / SSE, file search / read, structured output, error handling, cleanup. Two verified config / provider examples (`config.get`, `config.providers`) are added because research verified their shape. Banned patterns: `createOpencodeTui()` non-interactive, implicit default model, untrimmed filePath, v1 / v2 mismatch without probe, exposed unauthenticated non-loopback server.

6. **Three-bucket issue model.** `10_known_issues_and_troubleshooting.md` separates verified current bugs (Open GitHub issues with URL + status + assignee + workaround), resolved historical issues (#42541 closed; v1.18.9 MCP-compat fix), and generic operational risks (CLI on PATH, port collision, default 5000 ms timeout, Windows `taskkill`, mixed SDK / server versions, generated-types drift). Each bucket has its own table shape; the mitigation is named.

7. **Live phase split at the natural safety seam (Phase 3E1 -> review boundary -> Phase 3E2).** The hard-triggered live phase is split into two phases with an am-review PASS boundary between them. Phase 3E1 executes **zero provider calls**: it builds the temporary harness outside the tracked repo, installs the SDK package, captures CLI / SDK / Node / Bun versions, runs all auth-free SDK / CLI / server / session / file / lifecycle checks, captures an evidence skeleton in the temp dir, and runs a PID-scoped cleanup rehearsal. Phase 3E2 runs **only after am-review PASS on 3E1**: it executes one bounded Zen primary SDK structured-output prompt (`session.prompt` with a tiny `json_schema`), a bounded raw `curl -N` against the **local loopback `/global/event` stream** (NOT the Zen provider endpoint) running concurrently with the Zen prompt, optionally the Go provider route per user choice A or B (see `## Go provider route -- user gate`), sanitizes the evidence into `opencode-sdk-agent-docs/11_live_validation.md`, performs PID-scoped cleanup, and runs the secret scan. **The review PASS is the gate; the writer does not advance 3E2 merely because they believe 3E1 is complete.**

8. **Process safety: PIDs only the harness spawned.** The harness records the **harness-spawned** process handle(s) / PID(s) returned by `createOpencode({ ... })` / `server.close()` / `child_process.spawn`. Existing `opencode` processes on the host are out of scope and **must not** be killed. Cleanup calls `server.close()` / `AbortController.abort()` in `finally`, then verifies that the recorded PID(s) are no longer running. There is **no** `Get-Process opencode` invariant and no global kill.

9. **Port safety: unique loopback port via stdlib / PowerShell.** The harness does not assume port 4096 is free and does not bind to a port already in use. The port strategy is documented in Phase 3E1 (planner-approved unique loopback allocation, implementable with stdlib / PowerShell; e.g., iterate `[System.Net.IPGlobalProperties]::IPGlobalProperties.GetActiveTcpListeners()` and pick a free high port in the loopback range, or use the OS ephemeral-port range). The harness records the actual port it bound to. If port allocation races (the chosen port is taken between selection and bind), the verdict is `FAIL-Harness` and the harness stops before any provider call. The plan does not assume `port: 0` unless the SDK source explicitly confirms `port: 0` translates to OS-assigned (writer must re-validate against `types.gen.ts` at write time; until then, the harness picks an explicit free port).

## Token-cap resolution

Research verified the v1 SDK `Session.prompt` body shape as `{ model: { providerID, modelID }, parts: Part[], noReply?: boolean, format?: { type: "json_schema", schema: JSONSchema } }` ([S1]; [Z14]; [Z15]). **No `max_tokens` field appears in this body.** Research did NOT verify a `usage` block in the SDK `Session.prompt` response either -- the companion Go research references `usage.prompt_tokens` / `usage.completion_tokens` only in the context of the OpenAI-compatible endpoint, not the SDK wire shape. The dossier does NOT promise `max_tokens` in SDK code and does NOT promise that SDK output is hard-capped at any token count.

The bounded live-validation prompt uses three layered caps:

- **Soft cap via small JSON schema.** The single Zen prompt is a `json_schema` response with a tiny object schema (`{ answer: { type: "string", maxLength: 16 } }`). The model's training to comply with JSON schema plus the schema constraint is the soft output cap; a compliant response is well under 16 tokens.
- **Hard cap via 30-second wall clock.** The harness wraps the prompt call in `AbortSignal.timeout(30000)` (or an equivalent wall-clock timer) so any model that does not respond within 30 seconds is aborted. The 30-second ceiling is below the documented 29-second SSE hang window (#43007) by zero margin only because #43007 reports a 29-second silent exit; the 30-second cap is documented as the SDK-side hard ceiling.
- **Optional session abort.** If `session.abort` is available in the SDK (research verified `session.abort` exists as a method on the Sessions namespace; [S2]), the harness can call `client.session.abort({ path: { id } })` as a graceful cancellation. Research did NOT verify the wire shape for `session.abort` so the harness re-validates against `types.gen.ts` at write time; if the wire shape is not verified at write time, the harness omits this step and relies on `AbortSignal.timeout` only.

**Residual cost ceiling, stated honestly.** With the soft + hard cap stack, a worst-case prompt is still bounded by the model's output limit (128k tokens for Zen V4 Flash Free; 384k for Go V4 Flash). The 30-second wall clock caps this in practice (a non-responding model is aborted before it can produce more than a small prefix), but a runaway model that emits 128k tokens within 30 seconds would still hit the documented output ceiling. The dossier records this residual as a transparency line in `11_live_validation.md` and as a per-row `cost_class` field in the evidence table.

**On `usage` field claims.** Research did NOT verify `usage.prompt_tokens` / `usage.completion_tokens` / `usage.total_tokens` field names in the SDK response. The plan MUST NOT assert that the SDK returns a `usage` block with these exact field names. The evidence table's `usage` column records `n/a` for SDK-path rows unless the writer verifies the field names at write time against `types.gen.ts`; if not verified, the row records `usage: not-verified` and the writer does NOT treat `usage` presence as a verdict signal.

## Go provider route -- user gate

The Go backup path is **gated**. The plan does NOT authorize a Go provider call in Phase 3E2 until the user explicitly chooses one of the two alternatives below at the Phase 2 confirmation gate. Until then, the Go provider route is marked `gated -- awaiting user choice` in the evidence table.

### Alternative A -- Safety-first (recommended)

If the Zen primary SDK prompt returns a known Zen incident verdict (`SKIP-FreeLimitError`, `SKIP-SSE-Hang`, or `SKIP-UpstreamIncident`), the harness runs **one** raw OpenAI-compatible Go request via `curl` (NOT via the SDK `session.prompt`) against `/zen/go/v1/chat/completions` with `max_tokens: 16`. The raw request uses the OpenAI-compatible envelope; the harness does NOT call `session.prompt` for Go. The route class is recorded as `raw-provider-diagnostic`.

**What this validates:** the Go provider / gateway availability and that a real model call reaches the Go subscription target.

**What this does NOT validate:** the SDK's Go route (`session.prompt` with `providerID: "opencode-go"`). The Zen primary already proves the SDK wire shape works for one provider; the raw Go request proves only that the Go gateway is reachable.

**Token cap:** `max_tokens: 16` on the raw `curl` body is verified for the OpenAI-compatible envelope.

### Alternative B -- Full Go SDK fallback

The harness calls `client.session.prompt(...)` with `providerID: "opencode-go"`, `modelID: "deepseek-v4-flash"`, using a tiny JSON schema with `maxLength: 16` on the answer field plus `AbortSignal.timeout(30000)` and an optional `session.abort` call.

**What this validates:** the full SDK wire shape for the Go route (the same shape that the Zen primary proved, just with a different `providerID`).

**Token cap:** there is **no verified hard token cap** on the SDK path. The 30-second wall clock is the only hard ceiling. A runaway model could, in the worst case, emit up to the model's output limit (384k tokens for Go V4 Flash) within 30 seconds. The residual is stated honestly in the evidence row's `notes`.

### Default until user choice

Until the user explicitly chooses A or B at the Phase 2 confirmation gate, the Go provider route is **not authorized** in Phase 3E2. Phase 3E1 does not run any Go calls (it runs zero provider calls). Phase 3E2 runs the Zen primary + the local loopback raw SSE diagnostic; if the Zen primary returns a known incident verdict, Phase 3E2 records the verdict and **stops**, leaving the Go alternative selection for a follow-up user gate.

## Verdict taxonomy

Every row in `11_live_validation.md` carries exactly one verdict from the closed set below. The lint pass rejects any verdict not in this set. `FAIL-Harness` is NEW (added in refinement 3).

**Success / failure (the writer can act on these directly):**
- `PASS` -- evidence matches expected exactly.
- `FAIL-SDK` -- SDK threw, returned a malformed response, returned `info.error` set, or returned a non-`ok` text body where the prompt asked for `ok`.
- `FAIL-Evid` -- evidence record missing required fields, null where required, or wrong type.
- `FAIL-Cleanup` -- harness detected that a harness-spawned PID / process handle is still running after `server.close()` / abort in `finally`. Recorded PID(s) listed in the row.
- `FAIL-Secret` -- secret pattern found in the working tree. HARD STOP; the writer aborts the matrix immediately.
- `FAIL-Health` -- 5xx response from `GET /global/health`.
- `FAIL-VersionSkew` -- CLI / SDK outside compatible range (1.x vs 2.x, or major gap) AND the failure ties to skew; STOP and surface.
- `FAIL-Struct` -- structured output parse failed; response did not match the json_schema (model returned non-JSON or wrong keys).
- `FAIL-Harness` -- harness misconfiguration: port allocation race, port-bind failure, evidence skeleton missing required columns, or harness-write attempted to the tracked repo. STOP before provider calls. **NEW (refinement 3).**
