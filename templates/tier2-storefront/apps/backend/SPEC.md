# SPEC — apps/backend (Medusa 2 Path B)

App-specific spec for the Medusa 2 backend. The full template spec is at `../../SPEC.md`; this file only covers what is unique to the backend.

## Surface

- **REST API** under `/store/*` (customer-facing) and `/admin/*` (merchant-facing).
- **Custom route** at `src/api/store/products/route.ts` — `GET /store/products?limit=6&offset=0`.
- **Link module** at `src/links/product-category.ts` — wires Product ↔ Category many-to-many.
- **Seed script** at `src/scripts/seed.ts` — idempotent validator + dry-run; full DB writes deferred.
- **Middleware** at `src/api/middlewares.ts` — global CORS + cache-control headers.

## Data

- Postgres tables: `product`, `product_variant`, `product_category`, `product_category_product`, `customer`, `cart`, `order`, `order_line_item`, etc. (MikroORM-managed; scaffold ships `medusa-config.ts` only, no manual SQL).
- Migrations folder: `medusa-db/migrations/0001_init/auto-generated.sql` (placeholder; real migrations generated by `medusa db:generate`).

## Env

- `DATABASE_URL` (Postgres connection string, required)
- `REDIS_URL` (Redis connection string, optional in dev)
- `STORE_CORS`, `ADMIN_CORS`, `AUTH_CORS` (comma-separated origins)
- `JWT_SECRET`, `COOKIE_SECRET` (32 bytes random)
- `NODE_ENV` (`development` / `production`)
- `PORT`, `HOST` (defaults: 9000, localhost)

## Deferred items (this app)

These are env-blocked on Windows for Phase 3.4:

1. `medusa db:migrate` against a real Postgres database.
2. `medusa db:seed` end-to-end against a real Postgres database.
3. `medusa develop` / `medusa start` long-running server (verifiable only at deploy time, not in scaffold).
4. Admin dashboard customizations (`src/admin/widgets/*`).
5. Custom subscriber for `checkout.session.completed` (deferred to storefront's webhook handler, which delegates to a Medusa subscriber that doesn't exist yet).

## Tests

- `tests/seed.test.ts` — validates `data/product-seed.json` shape, asserts 6 products × 3 categories × 2 products per category.
- `tests/smoke-backend.test.ts` — mocks Medusa DI container; asserts `GET /store/products` returns `{ products, count }` shape with default pagination; asserts 400 on bad limit/offset.

## Why tests don't need a database

The route handler uses `req.scope.resolve("productModuleService")` — a DI pattern. Tests inject a mocked service via `vi.fn().mockResolvedValue([...])`. `medusa-config.ts` is loaded only when the dev server starts; tests don't import it.

If a future test wants to exercise the full Medusa container (services + Postgres), use `pg-mem`:

```ts
import { newDb } from "pg-mem"
const db = newDb()
const client = db.adapters.createPg() // returns a pg-compatible client
// inject client into a Medusa container...
```

This pattern is heavier than the unit tests above and isn't in scope of Phase 3.4 scaffold.
